# Vitrail — Field installer (§XXIX)

🇫🇷 [Version française](README.fr.md)

A "**1 payload, several channels**" provisioning CLI tool. It lets a technician install Vitrail on a
player with a minimum of steps and zero knowledge of the per-OS details.

> **Status: the 3 network channels are validated on hardware.**
> **Android (ADB)** ✅ validated on hardware (MINIX) · **Windows (WinRM)** ✅ validated on hardware
> (fresh Win11 25H2 VM) · **SSH** (Linux/RPi already installed) ✅ validated on hardware (RPi in
> service) · **BrightSign** (ZIP on SD card) = ⚠️ **NEVER yet validated on hardware against the
> ONLINE criterion** — the driver wrote `provisioning_token` (unreadable by the autorun, which
> reads `token`); this has been fixed, and still needs to be validated on a real BrightSign at the
> next opportunity. ChromeOS/extension = out of scope.
>
> ⚠️ **This README once announced "validated on hardware" before it was.** The hardware validation
> found **14 defects**: none of the three channels actually set up a player. The cause of the
> illusion fits in one sentence — **validation stopped at "the script started", never at "the
> player is online"**. In between, the SSH channel wrote no configuration at all. ⇒ **the only
> validation criterion for a channel is the player going ONLINE**, never a script's exit code.
>
> 👉 **To install a player at a customer site: `docs/RUNBOOK_POSE_PLAYER.md`** (this README
> describes the tool; the runbook describes the steps).
>
> **Direction**: the real need = **prepare/configure players quickly and simply** on the actual
> target OSes (Android, Debian 12, Windows 11, RPi, BrightSign). Chosen method = **cloned golden
> master (Clonezilla/PXE) + injection of a per-machine config bundle** (token/name/network), on the
> generalized BrightSign model. The "bare x86 box → Alpine+Chromium appliance" channel (greenfield
> x86) was **abandoned** (yet another player type nobody asked for, too fragile). See
> `docs/PLAN_PROVISIONING_PLAYERS.md`.

## Principle

```
auth CMS  →  payload (généré ou chargé)  →  driver OS  →  vérif online  →  rapport
```

(CMS auth → payload (generated or loaded) → OS driver → online check → report)

The **payload** (`signflow-provision.json`) carries: `ref`, `os`, `backend_url`, `token` (`sfp_`),
`network`, `options`. It is generated by the CMS (Provisioning page → "Generate payload", or
via the `POST /orgs/{id}/provisioning-payload` endpoint) and pre-creates the player on the CMS side
(offline) → the device **re-attaches** to it on registration (deterministic verify, **zero
duplicates**).

## Installation

```bash
cd installer
python -m pip install -r requirements.txt
# outil : python -m signflow_provision  (ou packagé en exe via PyInstaller)
```

## Authentication — operator key (recommended)

The tool authenticates with **either** an org-admin JWT (`--token`, **expires in 15 min** → must be
copied again and again), **or** a long-lived / revocable / provisioning-scoped **operator key**
`sfk_` (recommended). The org-admin generates it **once** in the CMS (**Provisioning → "Operator
key"**):

```bash
# Config UNIQUE sur la machine du technicien
# (stockée dans %APPDATA%\signflow\provision.json sous Windows — cas nominal du technicien —,
#  ~/.signflow/provision.json sinon ; le chmod 600 n'a d'effet que sur POSIX)
signflow-provision --cms https://cms.example.com --key sfk_… --save-config
```

(One-time configuration on the technician's machine, stored in `%APPDATA%\signflow\provision.json`
on Windows — the technician's usual case — and in `~/.signflow/provision.json` otherwise; the
`chmod 600` only has an effect on POSIX.)

→ after that, **no more `--cms`/`--token`/`--key` to re-enter**. Alternatives: the environment
variables `$SIGNFLOW_CMS` / `$SIGNFLOW_KEY`. The key is **provisioning-scoped** (create a payload +
read a player's status) — never general org-admin rights; it can be revoked from the CMS. ⚠️ It
**expires** (default **90 days**, adjustable up to 730 at creation) — a "CMS authentication
refused" months later is most likely the key.

## Usage

`signflow-provision` = the PyInstaller exe; in development, `python -m signflow_provision`. The
examples assume the key is configured (`--save-config` above); otherwise, add
`--cms <url> --key sfk_…`.

```bash
# Android — crée un nouveau player, génère le payload et provisionne par ADB
signflow-provision --ref "Boutique Lyon - Vitrine" --os android \
  --ip 192.168.1.50 --apk app-release.apk

# Ré-attache à un player existant (reprovisioning sans doublon)
signflow-provision --os android --ip 192.168.1.50 --reattach 42 --apk app-release.apk

# Linux/RPi déjà installé (SSH)
signflow-provision --ref "NUC Réserve" --os linux --ssh signflow@192.168.1.60

# Windows déjà installé (WinRM) — dépose la config ; --source lance install.ps1
signflow-provision --ref "PC Accueil" --os windows \
  --winrm 192.168.1.70 --winrm-user Administrateur --winrm-password '***' \
  --source 'C:\signflow\player-windows' --start-task

# BrightSign (écrit config.json à copier sur la SD)
# ⚠️ le driver écrivait la clé `provisioning_token` au lieu de `token` (illisible par l'autorun) —
# corrigé le 2026-08-16 ; canal jamais validé HW au critère ONLINE à ce jour
signflow-provision --ref "Vitrine BS" --os brightsign --out ./sd-out

# Réutiliser un payload généré depuis l'UI (Provisioning → « Générer un payload »)
signflow-provision --payload signflow-provision.json --ip 192.168.1.50 --apk app-release.apk

# Répéter les gestes sans rien exécuter
signflow-provision ... --dry-run
```

In order, the examples above:
- Android — creates a new player, generates the payload and provisions over ADB.
- Re-attaches to an existing player (reprovisioning without a duplicate).
- Linux/RPi already installed (SSH).
- Windows already installed (WinRM) — drops the config; `--source` runs `install.ps1`.
- BrightSign (writes `config.json` to copy onto the SD card). ⚠️ The driver wrote the
  `provisioning_token` key instead of `token` (unreadable by the autorun) — now fixed; the channel
  has never been validated on hardware against the ONLINE criterion so far.
- Reuses a payload generated from the UI (Provisioning → "Generate payload").
- Rehearses the steps without executing anything.

Network is OPT-IN: `--wifi-ssid/--wifi-psk` or `--static-ip/--mask/--gw/--dns`.
Display options: `--resolution 1920x1080 --rotation 90`.

**Diagnostics** (offline, no CMS needed) — which channels are usable here:
```bash
signflow-provision --selftest
```

## Packaging as an .exe (PyInstaller)

For a technician **without Python**, the CLI is frozen into a standalone exe (Windows):

```bash
pip install -r requirements.txt pyinstaller
pyinstaller --clean signflow-provision.spec
# → dist/signflow-provision.exe (~13 Mo, onefile)
dist\signflow-provision.exe --selftest      # vérifie les canaux embarqués
```

(Output: `dist/signflow-provision.exe`, ~13 MB, onefile; `--selftest` checks the embedded
channels.)

The Windows driver imports `winrm` **lazily** (so as not to impose it on the other OSes) → the
spec forces collection of the WinRM chain (`winrm`/`requests_ntlm`/`spnego`/`xmltodict`) as hidden
imports. **Install `pywinrm` BEFORE the build** so that the Windows channel is embedded (otherwise
the exe works for Android/SSH/BrightSign but not WinRM — `--selftest` reports it). `adb` (Android)
and `ssh` (Linux/RPi) remain external system tools, not embedded in the exe.

## Channels per OS

| OS | Channel | Foothold the technician must open |
|---|---|---|
| **Android** | ADB over IP | USB debugging + authorized ADB key; Device Owner ⇒ factory-fresh device **without a Google account**. |
| **Linux / RPi** (installed) | SSH/SCP | SSH enabled + credentials. |
| **Windows** (installed) | WinRM/PSSession | WinRM enabled (`Enable-PSRemoting -Force`) + **administrator** account. `pywinrm` required on the tool side. |
| **BrightSign** | SD card | Generate the complete SD card from the CMS, copy the produced `config.json` onto it. ⚠️ Driver fixed (`provisioning_token` → `token`); never validated on hardware against the ONLINE criterion. |
| **Debian/Windows/RPi** (to be prepared) | **cloned master + config bundle** | Clone an OS+player master, inject a bundle (token/name/network). See `docs/PLAN_PROVISIONING_PLAYERS.md`. |
| ChromeOS / extension | — | Out of scope (Google / browser enrollment). |

## Security

- The payload contains an **`sfp_` token** → treat the file/QR code as a **secret** (single use,
  TTL). Log nothing in clear text on the CMS side.
- The tool handles device credentials (ADB/SSH) → do not hard-code them.
- TLS verified by default (`--insecure` reserved for development).

## Capability check (pre-install)

`signflow_check.py` — a **standalone, stdlib-only** script (no pip) to run **on a candidate
machine** (Linux / Windows / RPi / macOS) to decide whether it can run a player. It returns a
verdict **VALIDÉ · VALIDÉ AVEC RÉSERVES · NON VALIDÉ** (validated · validated with reservations ·
not validated) (console + JSON + HTML).

```bash
python3 signflow_check.py --backend https://cms.example.com --profile fhd
python3 signflow_check.py --profile 4k --json rapport.json --html rapport.html
```

It checks: supported OS/arch, CPU cores, RAM, free disk, screen resolution, **hardware video
decoding** (GPU / `/dev/dri` / V4L2), **clock sync (NTP)** — required for LAN sync — and
**backend reachability** (DNS + TCP + `/health` + latency). Profiles: `fhd` (1080p, default) or
`4k` (requires more CPU/RAM + hardware decoding). Exit codes: 0 = validated, 1 = reservations,
2 = not validated (usable in a deployment script).

**Windows exe** (for a technician without Python):
```bash
pip install pyinstaller
pyinstaller --onefile --name signflow-check signflow_check.py
# → dist/signflow-check.exe (double-cliquable / en ligne de commande)
```
(The resulting `dist/signflow-check.exe` can be double-clicked or run from the command line.)
On Linux/RPi, `python3` is already present → run the `.py` directly.

> **Android / BrightSign / ChromeOS**: Python is not run on the device. These players
> **self-report their capabilities** (decoding, resolution, disk) to the CMS via `capabilities.json`
> at installation + the `player:status` heartbeat → visible in the player drawer / the NOC dashboard.

## Android provisioning via intent

The Android app accepts a **provisioning intent** (no keyboard driving):

```
adb shell am start -n app.vitrail.player/.SetupActivity \
  -e backend_url https://cms.example.com -e token sfp_…
```

`SetupActivity` auto-fills + auto-registers. Requires the **release** APK ≥ the version that
exports `SetupActivity` (§XXIX).

## Windows provisioning via WinRM

Windows has **no USB autorun** (blocked since Win7): on an **already installed** PC, the channel is
**WinRM**. The driver remotely reproduces `player-windows/install.ps1` (if `--source` is given),
then drops the provisioning `config.json` read by the Electron player:

```
%APPDATA%\signflow-player-windows\config.json
  { "backend_url": ..., "org_token": "<sfp_…>", "player_name": "<ref>" }
```

On first launch, the player self-registers (`POST /players/register`), exchanges `org_token` →
player token and **re-attaches** to the player pre-created on the CMS side (zero duplicates).

**Foothold** (on the target machine, once):
```powershell
Enable-PSRemoting -Force        # active WinRM (5985 http / 5986 https)
```

**Driver options**: `--winrm host[:port]`, `--winrm-user`, `--winrm-password`,
`--winrm-transport {ntlm|basic|credssp|kerberos}` (default `ntlm`, encrypts the message over 5985),
`--winrm-https` (5986), `--windows-user` (the **kiosk** account whose `%APPDATA%` receives the
config, default = `--winrm-user`), `--source` (remote `player-windows` folder → runs `install.ps1`),
`--start-task` ((re)starts the "SignFlow Player" scheduled task).

> Without `--source`, the driver **only drops the config** (player assumed already installed). Static
> network configuration is not applied automatically on Windows (MVP) — coming via the **config
> bundle** (`docs/PLAN_PROVISIONING_PLAYERS.md`). A **blank Windows box** = install Windows + the
> player once, turn it into a **cloned master**, then inject the bundle per machine.
